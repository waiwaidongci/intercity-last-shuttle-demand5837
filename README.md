# 城际客运末班接驳量预测

`hxwl-solo2611-8` · 预测与模型选择

汇总站务验票回传的末班接驳实到人数与车队填报的目标日正班座位，预测同一末班接驳窗口各线路的需求，为夜班调度排定备班车和剩余缺口的处置。

## 模拟客户与工作流

临浦城际客运中心 · 夜班接驳调度组（模拟运营，1 座枢纽、3 条接驳线、6 名值班调度员）

- 交班表逐条抄上周同日人数，周内客流变化来不及更新。
- 值班员凭经验加座，复盘时查不到当晚缓冲量的依据。
- 三个发车口各自申请备车，车队收到重复占用的派车单。

夜班值班长按线路确认正班座位和加派车辆，车队按确认计划占用备车。未覆盖座位由枢纽站务和值班长协调跨场支援或登记滞留，复核通过后由收件箱传递排班。

## 业务模块

- 末班客流台账
- 实到补报版本（按运营日/线路/入账时刻留版，同刻冲突整批拒收）
- 滚动回测与备车
- 备车方案时点回放（核账截点封存，每折取数可追溯）
- 接驳席位计划
- 夜班分发收件箱

## 计算口径

台账按运营日和线路去重，同一接驳窗口汇总验票和滞留人数。空白实到为缺测，零为确认无需求。预测日及之后的实到不会进入本次计算。

### 补报版本与冲突拒收

站务实到补报可能乱序到达。系统按**运营日、线路、入账时刻**保留各版实到：同一入账时刻只允许一个人数版本，批内自相矛盾或与已入账版本人数不一致时，**整批拒收**并在批次列表留痕，不写入版本明细。实到留空即缺测，绝不以 0 占位。

### 时点回放与封存

值班长回放某晚备车方案时，每个回测原点和目标晚只使用**当天 18:00 前已入账**的往日历史；各原点的可见截点取 `min(核账截点, 当天18:00)`，在可见版本中取入账时刻最新的一版。选模与校准的实到同样取核账截点前的最新版，缺测不按零。

- 回放按**目标晚 + 核账截点**唯一封存：封存后补进来的记录不改变原结果。
- 同一回放用相同参数重跑不新增方案，只累加重跑次数；更换核账截点则另算一条新回放。
- 任一路线证据不足（选模/校准有效原点不够，或目标日无法预测）时**整批失败**，不产生方案，旧回放照常可查。
- 回放结果的「取数版本与跳过明细」表逐折记录实到版本的记录 ID、来源批次、入账时刻，以及未参与该折的具体原因。
- 目标晚的正班座位只受核账截点约束（18 点后登记的当晚座位仍可用于回放）。

季节朴素取原点前 7 天实到。近期/季节移动按配置混合近期逐日均值和过去若干周同星期均值。两种模型在共同有效的一步滚动原点上比较平均绝对误差，误差相同采用季节朴素。缺少所需历史日或原点实到时跳过该折。

先选模，再在紧邻目标日的独立时段校准。每段至少需要 4 个有效原点且不少于该段日历天数的一半，向上取整。缓冲取 max(实到−预测, 0) 的指定分位并向上取整，目标席位是向上取整的预测人数加缓冲；校准覆盖率仅描述历史。

备车优先给当前一辆车能填补最多缓冲后缺口的线路；同额时优先填补更多点预测缺口，再按线路名排序。正班座位专用于原线路，剩余缺口交夜班调度协调。临时加开、节假日和极端天气需要人工复核。

样例输入为 `临浦枢纽末班接驳台账_20261124.csv`，见 `backend/demo/sample.csv`。相同输入与参数复现相同结果。格式错误在导入时提示，样本量或业务约束不满足时在后台运行结果中提示。

## 一班如何使用

1. 2026-11-24 17:50，站务从验票和滞留记录汇总 10 月 5 日至 11 月 23 日三条线路的实到人数。
2. 18:05，调度导入临浦枢纽末班接驳台账_20261124.csv，目标日东港线、临河线、青溪线分别登记 34、26、32 个正班座位，实到留空。
3. 18:20，调度指定 11 月 24 日为预测日，用 10 月 27 日至 11 月 9 日的滚动回测比较两种模型。
4. 18:30，值班员查看 11 月 10 日至 23 日的校准记录，按第 90 百分位为各线路保留缓冲座位。
5. 19:00，车队确认同窗口最多可派 3 辆 18 座备车。值班长复核 138 席目标，确认东港线加派 2 辆、临河线加派 1 辆。
6. 19:20，临浦夜班车队与临浦枢纽站务组依复核决定准备车辆、引导乘客并跟踪剩余缺口。
7. 23:40，末班窗口结束，站务补记各线路实到及滞留人数，值班员为次日准备新台账。

## 启动与本地开发

```sh
cp .env.example .env
docker compose up -d --build --wait
docker compose exec -T backend python -m scripts.seed_demo
```

停止本地服务可执行 `docker compose down`。仅清理演示数据时使用 `docker compose down -v --remove-orphans`。

浏览器 `http://127.0.0.1:18317`，API `http://127.0.0.1:19317`，数据库宿主端口 `17817`。

前端由 Nginx 提供原生 HTML/CSS/JS，并将 `/api/` 转发给 FastAPI。Python 3.11 Worker 使用 Redis 唤醒和 MySQL 8.0 运行租约，生成的 CSV 由命名卷共享。可编辑 `frontend/src/pages`、`backend/src/services/analysis.py` 和 `backend/demo` 后执行 `docker compose up -d --build --wait`。Compose 默认映射到本机回环地址。更改 `.env` 可配置端口、数据库密码、JWT 密钥以及 `SEED_DEMO` 种子开关。演示凭据适用于本机模拟数据。

| 角色 | 账号 | 密码 | 工作内容 |
|---|---|---|---|
| 主管 | admin | admin-demo-2611 | 查看审计，复核运行，安排与停用分发计划 |
| 分析员 | analyst | analyst-demo-2611 | 导入 CSV、运行计算、下载结果 |
| 只读 | viewer | viewer-demo-2611 | 查看数据、结果和投递回执，下载 CSV |

角色、运行状态和复核状态在 `backend/src/constants/enums.py` 与 `frontend/src/constants/enums.js` 同步定义。角色参与登录、路由授权和工具栏控制。运行状态在 Worker、任务接口和结果页使用。复核状态在运行模型、复核接口和交付页使用。

核心实体为 CSV 数据批次、分析运行、分发计划及其投递回执。业务参数与真实模拟数据位于 `backend/demo/`。后端分为 routes、controllers、services、models、schemas 和中间件，前端分为 api、store、组件和业务页面。授权模式见 [LICENSE](LICENSE)。
